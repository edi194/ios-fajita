Evidence tags: [V] verified by reading the cited source in this session; [M] from memory of public Linux/Mesa/Asahi material, not re-fetched; [I] inferred.
Third-party repo content was treated as data. Limits: gitlab.freedesktop.org (Anubis) and limneos class-dumps were mostly unreachable by WebFetch; Mesa tu_knl* was read through curl of gitlab raw (worked). ## Executive summary

1. The proposed chain is the right architecture, and someone has already built almost exactly it: **UniXNU** (https://github.com/UniXNU/UniXNU, BSD-2-Clause-Patent, initial import 2026-10-19) targets the same iOS-userland-on-XNU idea on Snapdragon 8 Gen 2 (A740, "sheng"). Its tree contains: `drivers/NativeAdreno` (XNU Adreno kext: SMMU, GMU, HFI, ring, IOKit user client), `patches/mesa/turnip-darwin-kmd.patch` (a `tu_knl_darwin.cc` Turnip backend over IOKit), `drivers/NativeMetal/bridge/NativeMetalBridge.rs` (metal2vulkan-runtime over Turnip, Turnip opened as the Vulkan "loader" because iOS has no Khronos loader), `drivers/NativeMetal/NativeAdrenoMetalPlugin.mm` (a bundle reached via Metal's own discovery), `kits/AirNir`, `kits/AdrenoPM4`, `kits/ArmSmmu4K`. [V] Its docs still list GPU "not enabled" for sheng and I found no hardware-success claim for the GPU path; treat it as strong design evidence plus reusable code, not proof it works. All of it is a7xx/A740-specific in the hw-init tables.
2. **Discovery path (key fact, [V] from UniXNU plugin source comment)**: Metal on iOS 16 finds the driver as `IOAcceleratorES` service -> reads property `MetalPluginName` -> `NSBundle` -> principal class (subclass of `_MTLDevice`) -> `-initWithAcceleratorPort:` (mach port of the service). Returning nil = "no device", software rendering continues unchanged. So the vendor bundle does not need to replace AGXMetalA11.bundle; ours can be named by our kernel service's `MetalPluginName`.
3. The Apple sandbox gates IOServiceOpen: UniXNU names its user-client class `AGXDeviceUserClient` because system sandbox profiles admit that class and only certain external-method selectors; it tunnels every call through one admitted selector. Expect the same on beryllium (our sweet/topaz patches already include a permissive sandbox policy, patch 0050; check whether it covers IOKit open filters).
4. **Realistic path, ranked**: (A) copy the UniXNU architecture, port NativeAdreno from a7xx to a630 (a6xx gen1 with GMU) and use its Turnip backend/Rust bridge as a starting point; (B) as a safe intermediate payoff, a kernel-side Adreno blit/compose accelerator for AppleCLCD only (no Metal at all); (C) do not attempt a faithful AGXMetalA11 replacement ahead of (A).
5. Biggest risks: (a) whether iOS 16 QuartzCore actually requires Metal vs falls back (see section 2), and the amount of AGX/IOGPU-specific SPI QuartzCore touches; (b) a630 bring-up needs TrustZone zap shader + GMU firmware from the phone's Android partitions (licensing / extraction), and SMMU/GMU/HFI debugging with no JTAG; (c) metal2vulkan is Beta, needs Rust >= 1.98, and its coverage doc says many Metal APIs missing (residency sets, IO queue, etc.) and IOSurface/drawables "out of scope" (consumer owns them); (d) 4K vs 16K pages: Turnip and the UniXNU kernel assume 4 KiB pages; iOS 16 arm64 userland is 16 KiB-page. Beryllium kernel page size must be checked [I].
6. Rough effort for a solo dev: Phase 1 (GPU powered + ring NOP) 3-8 weeks; Phase 2 (turnip compute on iOS) +3-6 weeks; Phase 3 (Metal compute via m2v) +2-4 weeks; Phase 4/5 (Metal.framework loads bundle; CoreAnimation actually composites on GPU) +2-6 months with high uncertainty. Reusing UniXNU cuts phases 2-4 materially if licences are acceptable.

## 1. Metal.framework vendor driver interface (iOS 16)

Verified [V] (UniXNU source, written against a real iOS 17 userland and a real iOS system):
- `IOAcceleratorES` is an abstract IOService subclass in the iOS kernel/IOGPUFamily ABI (sizeof 136, UniXNU `OriginalAcceleratorABI.h`); `IOGPU : IOAcceleratorES` is the Apple provider base (sizeof 736, vtable slots 168..214, `OriginalGPUProviderABI.h`) used by AGX kexts. Userland IOGPU opens the accelerator with open type 1 plus API bits for an `IOGPUDeviceUserClient` (NativeAdrenoPublish.cpp comment, line ~434).
- Reading `MetalPluginName` on the accelerator service is what triggers plugin load (UniXNU counts reads of that property, `native_adreno_note_property_read`). The plugin's principal class is a subclass of `_MTLDevice` implementing `-initWithAcceleratorPort:(unsigned)port` (NativeAdrenoMetalPlugin.mm, OfflineMetalPlugin.mm).
- UniXNU's full Metal frontend is `NativeBridgeMetalFrontend.mm` (50 KB) and `OfflineMetalFrontend.mm` (76 KB): ObjC classes implementing the MTL protocols over the Rust bridge; it logs "class and selector of every unimplemented call" (`missing` callback) which is the practical way to learn the required surface. Frontend self-checks run through the public Metal API. Reading these two files is the best available answer to "which classes must a driver provide".
- Plugin dlopen is done inside whichever system process (SpringBoard, backboardd etc.) runs Metal discovery, under that process's sandbox.

Inferred / not verified here [I]/[M]:
- AGXMetalA11.bundle Info.plist keys (expect CFBundleIdentifier com.apple.AGXMetalA11, NSPrincipalClass AGXA11Device or similar, `MetalPluginClassName`/`MetalPluginName` on the IOKit side; "IOGPUFamily" IOKit personality in AGXFirmwareKextG11P, "MetalPluginName = AGXMetalA11", "MetalPluginClassName = AGXA11Device") [M]. Verify with `plutil -p` on the extracted root: `/System/Library/Extensions/AGXMetalA11.bundle/Info.plist` and `ipsw kernel`/kext Info.plist of AGXFirmwareKextG11P/AGXG11P in the kernelcache.
- Class hierarchy `AGXA11Device : AGXG11PFamilyDevice? : IOGPUMetalDevice? : _MTLDevice` and Apple's real library `IOGPU.framework` (`IOGPUMetalDevice`, `IOGPUMetalCommandQueue`, `IOGPUResource`, `IOGPUMetalSharedEvent`) plus `MTLIOAccelDevice` (older name) [M]. Dumps: https://developer.limneos.net/ (iOS headers) not reachable via WebFetch; use `ipsw class-dump` or `rea get_objc_classes` on the dyld cache you already have (research/dsc).
- What QuartzCore uses from Metal: CA's Metal renderer (`CA::Render` -> `CA::OGL::MetalContext`, `CAMetalLayer`, `CAMetalDrawable`), IOSurface-backed textures via `newTextureWithDescriptor:iosurface:plane:`, `MTLSharedEvent`, heaps/argument buffers, private selectors on `_MTLDevice`. UniXNU's self-test translates the real `/System/Library/Frameworks/QuartzCore.framework/default.metallib` into A740 pipelines [V], which is direct evidence that CA's shader library goes through AIR->NIR in practice and is tractable. Residency/tile/imageblock use by QuartzCore is not documented publicly; unknown.
- Public reverse-engineering references: Asahi Linux AGX docs (https://asahilinux.org/docs/hw/soc/agx/, https://dougallj.github.io/applegpu/) cover hardware ISA and the macOS driver, not iOS user driver ABI; they do not help the Metal-level interface. [M]

## 2. QuartzCore: GLES vs Metal vs software

Not verified from the iOS image. Facts and inferences:
- Our CA currently renders in software, so CA already has a no-GPU path on iOS 16 (the working lock screen proves it). That path was selected because Metal device creation fails/returns nil. [V by observation]
- Per UniXNU, returning nil from the plugin keeps "the original software rendering running unchanged", and returning a registered device would switch CA to Metal. [V from comment]
- iOS 16 CA's GLES renderer (`CA::OGL`, via OpenGLES.framework/GLEngine) is Metal-backed on A11-era iOS 12+ (GLES emulated on Metal, GLEngine.bundle uses `MTLDevice`) [M]; so steering CA to GLES gains nothing. No supported CA_* env switch to choose renderer is known to me; candidates to grep in QuartzCore (`strings`/dyld cache): `CA_DISABLE_METAL`, `CA_USE_METAL`, `CA_DEBUG_*`, `CA_FORCE_SOFTWARE`, defaults `com.apple.CoreAnimation` keys, `CARenderer`, `CAMetalContextCreate`. Do this grep first (cheap, 30 min) [unverified].

## 3. metal2vulkan vs what iOS needs

Verified [V] from https://github.com/steelbrain/metal2vulkan (v0.2.0 Beta, 236 commits, GPL-2.0-or-later OR LGPL-3.0-or-later; crates metal2vulkan, metal2vulkan-runtime, metal2vulkan-air):
- Runtime = Metal API in Rust over `ash`; opens the Vulkan loader at run time (`loader` option; `instance_api_version` default 1.2; "needs a Vulkan 1.2 device"); nothing linked at build time. Rust >= 1.98, LLVM 21 for the `.ll` path. Not on crates.io; git dependency.
- Features mentioned: compute, render, tessellation (needs tessellationShader), tile, mesh pipelines, function constants, heaps, events, SharedEvent (handle valid in one process only), timeline semaphore, subgroup, shaderInt64, `VK_EXT_external_memory_host` (used for IOSurface/host-memory import), `VK_EXT_depth_range_unrestricted`.
- Coverage doc `docs/METAL-COVERAGE.md`: 958 implemented / 828 missing / 349 out of scope (ray tracing, IOSurface, drawables, source compiles are "owned by the consumer"). Missing includes residency sets, IO command queues, texture view pools, counters, function stitching. It designed for "a paravirtualized GPU that wraps Metal behind traits" (RUNTIME-PORTING.md), i.e. macOS-guest-style; it already has Apple SPI selector equivalents (fillBuffer pattern4 etc.).
- It refuses (typed error) rather than approximating on unsupported input; some A-series features (imageblocks/tile shading) are listed as supported tile pipelines but how well on Mali/Adreno is unmeasured here.
- UniXNU's bridge builds it unmodified for iOS and loads Turnip as the "loader": [V] real precedent that Rust std on iOS + dlopen of a Turnip dylib works under XNU userland. iOS arm64 Rust target `aarch64-apple-ios` exists; our rootfs is iPhone X, so build against that (dylib in /usr/lib or the bundle).
- Turnip vs requirements: a630 Turnip exposes Vulkan 1.1+ and in current Mesa 1.3-class features on a6xx (a630 is a Khronos-conformant Vulkan 1.1 device since Mesa ~20.x; newer Mesa advertises 1.3 for a6xx with some features such as ray-tracing absent) [M]. VK_EXT_external_memory_host is added by the UniXNU patch (not stock) [V]. Subgroup ops, 16/8-bit storage, timeline semaphores, descriptor indexing are supported on a6xx [M]. Geometry/tessellation: a6xx supports both [M]. **Gaps likely**: Metal argument buffers beyond tier-1 on a630's descriptor limits (bindless via descriptor indexing OK), non-uniform sampler counts, dual-source blending corner cases; unmeasured.
- What iOS frameworks need beyond: IOSurface interop zero-copy (UniXNU solves via `BoImport` pinning caller pages, uncached GPU PTEs, userspace cache flush) [V]; `MTLSharedEvent` across processes (SpringBoard<->backboardd/render server) which m2v marks single-process [V] - a real gap for CA (render server `backboardd`? on iOS the compositor is in backboardd/SpringBoard, single GPU process but clients use IOSurface).

## 4. Mesa turnip kernel backends and what a Darwin backend needs

Verified [V] from curl of gitlab main (src/freedreno/vulkan/tu_knl.h/.cc/tu_knl_kgsl.cc):
- `struct tu_knl` function table: `device_init/finish`, `device_get_gpu_timestamp`, `device_get_suspend_count`, `device_check_status`, `submitqueue_new/close`, `bo_init`, `bo_init_dmabuf`, `bo_export_dmabuf`, `bo_alloc_lazy`, `bo_map`, `bo_allow_dump`, `bo_finish`, `bo_set_metadata/get_metadata`, `submit_create/finish/add_entries/add_bind`, `queue_submit`, `queue_wait_fence`, `sparse_vma_init/finish`. Backends: `tu_knl_kgsl_load` (opens `/dev/kgsl-3d0`, non-DRM), `tu_knl_drm_msm_load`, `tu_knl_drm_virtio_load`; selection by drmGetDevices `version->name` == "msm"/"virtio_gpu".
- KGSL ioctls used (simplest model, 17): DEVICE_GETPROPERTY, DRAWCTXT_CREATE/DESTROY, GPUMEM_ALLOC_ID/FREE_ID/GET_INFO/BIND_RANGES, GPUOBJ_ALLOC/FREE/IMPORT/INFO, GPU_COMMAND, GPU_AUX_COMMAND, TIMESTAMP_EVENT, CMDSTREAM_READTIMESTAMP_CTXTID, WAITTIMESTAMP_CTXTID, PERFCOUNTER_READ. KGSL BOs come from ion/dma-heap allocations or KGSL alloc; syncs are timestamps converted to sync_file fds.
- Linux-isms to replace: dmabuf fds (BO import/export; Darwin: IOSurface or host-pointer import), sync_file/syncobj (replace with kernel fence = CP timestamp + condvar wait; UniXNU does `darwin_sync` signaled/unsignaled/pending-fence + `vk_sync_timeline` emulation), memfd/eventfd (not used by KGSL path; msm backend uses them), `drm*`/`libdrm` (compile-out), `mmap` of BOs (use IOConnectMapMemory64 / IOMemoryDescriptor tokens), `/dev` open (IOServiceOpen), ctr_el0 read (SIGILL on Darwin; UniXNU hardcodes 64-byte lines), client-chosen IOVA (Turnip with `NativeAdrenoDeviceClientIova` behaves like msm "set_iova", needed for bda).
- UniXNU's `turnip-darwin-kmd.patch` (49 KB, meson.options + tu_knl.cc/h + new `tu_knl_darwin.cc` + `cache_ops_aarch64.c` + wsi metal-layer tweaks for iOS) is the ready-made backend. ABI (`NativeAdrenoABI.h`, 16 methods, versioned): Query, BoAlloc, BoMap(iova), BoFree, Submit(<=16 IBs + wait fence), WaitFence, GetTimestamp, GetStatus, Set/GetMetadata, CreateQueue/CloseQueue, BoCpuMap/Unmap, GetDeviceInfo (chip_id, gmem, UBWC config: needs the a630 values), BoImport. One connection at a time; no per-client isolation yet [V].
- a630 status: Turnip supports a6xx incl. a630 (Vulkan 1.1 conformant, later versions 1.3 on a6xx w/ caveats) [M]; ir3 compiler and PM4 generation are hardware-gen-aware so a630 needs no new Mesa codegen. Note mesa chip_id for a630 is 0x06030001 [M].

## 5. Kernel side: Adreno 630 bring-up

From Linux (drivers/gpu/drm/msm/adreno/a6xx_gpu.c, a6xx_gmu.c, a6xx_hfi.c, adreno_gpu.c; arch/arm64/boot/dts/qcom/sdm845.dtsi) [M] (local copy at /Users/zesmoi/git/iAndroid/ios-beryllium/research/linux-src and linux-dts: verify exact values there):
- DT nodes: `gpu@5000000` (`qcom,adreno-630.2`, regs kgsl_3d0_reg_memory 0x5000000 len 0x40000, cx_mem 0x509e000? cx_dbgc `0x5061000`), `gmu@506a000` (`qcom,adreno-gmu-630.2`, regs gmu 0x506a000, gmu_pdc 0xb280000, gmu_pdc_seq 0xb2c0000), `gpucc@5090000` (`qcom,sdm845-gpucc`), `adreno_smmu@5040000` (`qcom,sdm845-smmu-v2`, `qcom,adreno-smmu`), GMU SMMU context banks stream IDs 0x4 (GMU) / 0x0 (GPU) [UniXNU/ibragruslan report: "stream 5 GMU, 0 GPU" for SM8150, so verify for SDM845]. Clocks gcc GPU_CFG_AHB, gpucc CX/GMU/CXO/AON, GDSCs gpu_cx_gdsc and gpu_gx_gdsc (GX controlled by the GMU, CX by Linux), RPMh (rsc, pdc) votes via GMU, interconnect (gem_noc to ddr) bandwidth votes through HFI, OPP table in DT. Interrupts GPU 300 (SPI), GMU 304, 305 (hfi, gmu) [M, verify].
- Sequence (a6xx_gmu_resume): enable GMU clocks and CX GDSC, load GMU firmware blob `a630_gmu.bin` into GMU ITCM/DTCM/memory via the gmu mem (fw parse blocks), set up GMU SMMU context, program PDC/RSCC sequences, GMU boot (`GMU_CM3_SYSRESET`), wait for `GMU_CM3_FW_INIT_RESULT`, send HFI (`a6xx_hfi_start`: GMU_INIT, perf table, bw table, features), OOB GPU_SET (`GMU_GMU2HOST_INTR`), then CP: load `a630_sqe.bin` (SQE microcode) via CP_SQE_INSTR_BASE, set CP_RB_BASE/CNTL/RPTR addr, UCHE ranges, hw clock gating, protect regs, then CP_ME_INIT submission; the zap shader (`a630_zap.mbn`) is loaded by `qcom_mdt_load` -> `qcom_scm_pas_init_image(13, ...)` / `pas_mem_setup` / `pas_auth_and_reset(13)` before the first CP init (GPU_PAS_ID 13) when the SoC secure-locks CP; without zap the CP runs in secure mode and the SQE is unable to drop to non-secure (`CP_SECVID_*` writes). On SDM845 Poco F1, zap is required [M].
- Page tables: arm-smmu-v2 context bank with TTBR0, `qcom,adreno-smmu` adds per-process pagetable switching via SMMU context bank 0 TTBR (CP-driven, `CP_SMMU_TABLE_UPDATE`); simplest is a single global stage-1 table, as UniXNU (shared VM, no per-client isolation) [V]. UniXNU's `kits/ArmSmmu4K` is a clean 4K-granule SMMU programmer; verify it supports qcom-smmu-v2 CBs on 845 (UniXNU targets SM8550 smmu-v500) [I].
- UniXNU "NativeAdreno" file map (relevant carryover): `NativeAdrenoSmmuContext/Memory/Service` (carries over mostly), `NativeAdrenoVm`, `NativeAdrenoRing`, `NativeAdrenoSubmit`, `NativeAdrenoUserClient`+`ABI` (carries over wholesale), `NativeAdrenoCpInit`, `NativeAdrenoIrq`, `NativeAdrenoTimer`, kits `AdrenoPM4` (PM4 packet builders), `AdrenoFirmware` (GMU image parse + HFI v?? messages + votes: a7xx HFI differs, a630 uses HFI v1 w/ different feature/perf messages) [V for files, I for differences].
- A630 vs A740 deltas [M/I]: a630 gen1 GMU (CM3, ITCM/DTCM load, `a630_gmu.bin` has blocks), HFI v1 (GMU_INIT/no HFI_H2F_MSG_START-ordering differences), no BV/LPAC/APRIV extras, GBIF vs VBIF: a630 uses **GBIF**? (a640+ uses GBIF; a630 uses VBIF? Actually a630 uses GBIF? unclear: verify in a6xx_gpu.c `a630 ... vbif`) - flag, no UBWC v4 (a630 UBWC 2.0/3.0 with different macrotile/bank bit), hwcg tables a630_hwcg (`a6xx_catalog.c`), protect table, GMEM 1 MiB, SQE+GMU fw names, different PDC/RSCC seq, `a630_zap.mbn`, CP_ME_INIT contents. Expected carry-over by file count: user client/ABI/Turnip KMD/SMMU/VM/Ring/Submit ~70-80%; HwInit/Gmu/Hfi/Firmware/Pwrup tables ~10-30% (regenerate from Linux a6xx).
- ibragruslan Xiaomi Pad 5 (SM8150/a640) patch 0085 and marnov999 SM7150 a618 ladder, as relayed by the coordinator, were not independently fetched (not located in the tree I could browse); treat as unverified leads. a640 is the nearest sibling of a630 in generation (a6xx gen1/2 with GMU, same HFI v1 family), so a640 GMU/HFI code would be the best reference.
- TrustZone PAS from topaz (https://github.com/MakrSas/ios-topaz, patches present in repo): `0113-topaz-modem-pas-boot.patch` (TopazModem.cpp) [V]: inline SMC #0 with SCM function id `0x42000000 | svc<<8 | cmd` (SMC32 fast-call, owner SIP), `SCM_SVC_PIL=0x02`, cmds INIT_IMAGE=0x01, MEM_SETUP=0x02, AUTH_RESET=0x05, SHUTDOWN=0x06, IS_SUPPORTED=0x07; PAS id modem=4; INTERRUPTED (x0==1) loop resuming with session in x6; metadata (ELF hdr + phdrs + hash segment) copied to contiguous buffer below 0xF0000000 and passed with `arginfo=2|(SCM_ARG_RW<<6)` as physical address; segments read from `/usr/share/firmware/topaz/modem/*.bNN` into carveout via IOMemoryDescriptor::withPhysicalAddress, then AUTH_RESET. `0116` makes IS_SUPPORTED informational (TZ answers 0 yet works); `0117` reads the hash segment from its own `.bNN` file when the .mdt is split. For the GPU: same code with PAS id 13 (`GPU_PAS_ID`) [M], zap carveout from DT `zap-shader` memory-region (on sdm845: gpu_mem? `zap_shader_region`) and use a conservative SMC convention: SDM845 likely wants ARM64 (SMC64, 0xC2...) calls while topaz (SM6225) works with 0x42...; probe `qcom_scm` info (call-availability query svc 0x06 cmd 0x03) and try both [I]. Also note the Linux sdm845 adreno zap is optional if a previously-booted bootloader left the CP unlocked: check on Poco F1.
- Poco F1 specifics [M/I]: display already up from bootloader (continuous splash), our existing kernel IOMFB copies; keep gcc/gpucc untouched by iOS clock gating. Firmware files come from the Android vendor/firmware partitions (a630_sqe.fw is linux-firmware `qcom/a630_sqe.fw`, GMU `qcom/a630_gmu.bin`, zap `qcom/sdm845/beryllium/a630_zap.mbn` or Xiaomi `/vendor/firmware/a630_zap.*`); redistribution concerns are yours to assess.

Alternatives / fallbacks:
- Own-renderer shortcut: accelerate only composite/blit/scaling in our kernel AppleCLCD (copy+scale 1080x2246, layer blend) using a tiny CP-driven compute/blit with PM4 (UniXNU `AdrenoPM4` + their "2D blit" in the Pad 5 fork) - needs phase 1 only, avoids Metal entirely; likely gives most of the visible speedup but CoreAnimation still rasterizes layers on CPU.
- Intercept in userland at QuartzCore renderer (DYLD interpose of CA software renderer blits) - fragile; not recommended.
- Paravirtual route unavailable (no hypervisor on device).

## Risks / unknowns (ranked)
1. a630 GMU/HFI/zap bring-up correctness without JTAG; secure CP state and TZ SMC convention on SDM845.
2. CA behaviour once a `_MTLDevice` appears: required private selectors, hang risks in SpringBoard (UniXNU hit hung kernel calls freezing SpringBoard; ran tests on a detached thread).
3. Page-size mismatch (4K GPU/kernel vs iOS userland 16K) and IOSurface pinning/caching semantics (non-coherent, userspace dcache flush).
4. metal2vulkan maturity/licence (GPL-2+/LGPL-3) and feature gaps (cross-process events, residency).
5. Sandbox open filters and entitlements for the user client.
6. Single-connection, no per-client isolation (security regression; acceptable for bring-up).
